**Keep this file current.** The Architecture section below describes the app's state as of when
it was written. If a change adds/removes a layer, swaps a library, or closes one of the gaps

## Commands

Build and install (Windows: use `gradlew.bat`; this repo has been developed against a device connected via adb rather than Android Studio's run button):

```
./gradlew assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell am start -n com.schmodcast/.MainActivity
```

If multiple devices/emulators are attached, target one explicitly with `adb -s <serial> ...` (check `adb devices -l` first).

`adb` isn't guaranteed to be on `PATH` in every shell (notably: it isn't in either of Claude
Code's Bash/PowerShell tool shells on this machine, even though a device is normally attached).
If `adb` isn't found, read `sdk.dir` from `local.properties` (gitignored, so this path is
machine-specific) and call `<sdk.dir>/platform-tools/adb.exe` directly rather than concluding no
device is connected.

Other useful tasks:
- `./gradlew lint` / `./gradlew lintDebug` — Android Lint (no ktlint/detekt configured)
- `./gradlew clean assembleDebug` — full rebuild, useful after touching Room schema/KSP-generated code

There are no unit or instrumented tests in the repo yet (`app/src/main` is the only source set) — `testDebugUnitTest` / `connectedDebugAndroidTest` exist as empty AGP scaffolding only.

`local.properties` (gitignored) must set `sdk.dir` to a local Android SDK install.

## Critical build gotchas

- **AGP is pinned to 9.1.1** in `gradle/libs.versions.toml`. AGP 9.3.1 (and the matching Gradle 9.3.1) crashes applying to any module with `NoClassDefFoundError: org/gradle/features/binding/ProjectTypeBinding` — a genuine upstream bug, reproduced and isolated during initial setup. Don't bump `agp` without testing a real build first.
- **AGP 9.0+ has built-in Kotlin support.** Do not re-add the `org.jetbrains.kotlin.android` plugin — applying it alongside AGP 9.x throws ("no longer required for Kotlin support since AGP 9.0"). Only `org.jetbrains.kotlin.plugin.compose` and `org.jetbrains.kotlin.plugin.serialization` are applied as Kotlin plugins.
- Kotlin compiler options (jvmTarget, etc.) go in the `kotlin { compilerOptions { ... } }` block in `app/build.gradle.kts` — the legacy `android.kotlinOptions` DSL doesn't exist under AGP's new API.
- `androidx.compose.material:material-icons-core` (the only Material icons dependency in this project — no `-extended`) has a small, fixed icon set. Icons like `Icons.Filled.Pause` and `Icons.Filled.LibraryMusic` aren't in it and fail with "unresolved reference"; when core doesn't have what's needed, add a small hand-drawn vector drawable instead (see `res/drawable/ic_pause.xml`) rather than pulling in `material-icons-extended`.
- Room's `SchmodcastDatabase` uses `fallbackToDestructiveMigration(dropAllTables = true)` — this is a pre-release app with no real installs to preserve, so bumping `@Database(version = ...)` just wipes local data on next launch instead of requiring a migration. Revisit this once the app has real users.

## Architecture

Single-module app (`:app`). Kotlin + Jetpack Compose (Material 3). No DI framework (no Hilt/Dagger) — `SchmodcastApplication` acts as a manual service locator, lazily constructing the Room database and repository/manager singletons and exposing them via `Context` extension functions (`Context.subscriptionsRepository()`, `Context.episodeRepository()`, `Context.episodeDownloadManager()`) that Composables and the playback `Service` call directly rather than receiving injected dependencies.

### Navigation
One `NavHost` in `MainActivity.kt`, three bottom-nav tabs defined in `ui/nav/Destinations.kt`:
- **Queue** (start destination) — `ui/queue/QueueScreen.kt` + `QueueViewModel`
- **Library** — `ui/library/LibraryScreen.kt`, the subscribed-shows list
- **Search** — `ui/search/SearchScreen.kt` + `SearchViewModel`, iTunes Search API lookup with subscribe/unsubscribe

### Data layer
- `data/model/` — plain domain models (`Podcast`, `Episode`)
- `data/local/` — Room: `PodcastEntity`/`PodcastDao`, `EpisodeEntity`/`EpisodeDao`, `SchmodcastDatabase`
- `data/remote/` — `ItunesSearchApi` (Retrofit + kotlinx-serialization, JSON, for podcast directory search) and `RssFeedParser` (a small hand-rolled `XmlPullParser`-based RSS 2.0 reader — deliberately no XML/RSS library dependency); `NetworkModule` holds the shared `OkHttpClient` and Retrofit instance
- `data/SubscriptionsRepository.kt` — subscribe/unsubscribe against Room
- `data/EpisodeRepository.kt` — fetches and parses each subscribed podcast's RSS feed, keeps only episodes published in the last 60 days (`QUEUE_WINDOW`), exposes the merged queue as `Flow<List<Episode>>` sorted newest-first. `RssFeedParser`'s date parsing normalizes named US timezone abbreviations (PDT/PST/EDT/etc.) to numeric offsets before handing off to `DateTimeFormatter.RFC_1123_DATE_TIME`, which otherwise silently rejects them — a real feed (WordPress/PowerPress-style) hit this and dropped every episode.
- `data/download/EpisodeDownloadManager.kt` — downloads an episode's audio to app-internal storage (`filesDir/episode_downloads`), tracking per-episode `DownloadState` (NotDownloaded/Downloading/Downloaded/Failed) in a `StateFlow<Map<episodeId, DownloadState>>`. Runs on an app-scoped coroutine scope, not WorkManager, so an in-progress download doesn't survive process death. `PlaybackService.loadEpisode` reads `EpisodeEntity.localFilePath` and plays from that file when it exists on disk, falling back to streaming `audioUrl` otherwise — so a downloaded episode plays offline.
- `data/PlaybackStateStore.kt` — a thin SharedPreferences wrapper (not Room) holding the single scalar "which episode was last loaded" value; a dedicated table felt like overkill for one nullable string, and it's read synchronously from `PlaybackService.onCreate` before the queue Flow's first emission arrives.

### Resume playback position
`EpisodeEntity.lastPositionMs` persists each episode's seek point, and `PlaybackStateStore.currentEpisodeId` persists which episode was last loaded (independent of queue order — it can be an episode picked out of turn, not just the head). `PlaybackService` writes both: `loadEpisode` and the natural-transition handling in `onMediaItemTransition` (see Playback below) set `playbackStateStore.currentEpisodeId` whenever any episode becomes current (head, auto-advance, or out-of-order tap), and `lastPositionMs` is written via a `Player.Listener` — a 5s ticker while playing, immediately on pause (`onIsPlayingChanged`) and on any seek (`onPositionDiscontinuity`, which fires regardless of whether the seek came from the skip buttons, the progress slider, or a resume-seek), plus a final synchronous save in `onDestroy` (using `runBlocking`, since `serviceScope.cancel()` would otherwise cancel a just-launched save coroutine before it ran). On the first queue emission after process start, the service looks up `playbackStateStore.currentEpisodeId` in the freshly-collected queue and loads that episode (seeking to its `lastPositionMs`) instead of unconditionally loading the queue head; if that episode is no longer in the queue (played/pruned), it falls back to the head. Resuming at `lastPositionMs` isn't only a launch-time concern: the player's timeline holds the *entire* queue at once (see Playback below), and any episode in it can already be partway through, so `onMediaItemTransition` explicitly seeks to `lastPositionMs` when ExoPlayer auto-advances onto one, the same way `loadEpisode` does via `setMediaItems`'s `startPositionMs` param when explicitly loading one. `EpisodeRepository.refreshFeed` preserves `localFilePath`, `lastPositionMs`, and `played` across a feed refresh (by copying them from the pre-existing row before `insertAll`'s REPLACE), since `QueueViewModel.init` triggers a refresh on every app launch — without that preservation, resuming a position would get silently reset to 0 by the very refresh that runs before playback restores. `played` needs the same treatment for a less obvious reason: `RssItem.toEntityOrNull` builds each candidate fresh from the feed with `played` defaulting to `false`, so any previously-played episode still inside `QUEUE_WINDOW` (60 days — easily true right after marking something played) would otherwise get resurrected into the queue by REPLACE on the very next refresh.

### The Queue's core behavior
There is deliberately no episode-browsing UI and no manual reordering: every subscribed podcast's recent episodes are merged into one global, date-sorted queue, and "current" is always whatever sits at its head.

`QueueScreen.kt`'s now-playing card has two content layouts sharing one `NowPlayingCard` composable: a compact `CollapsedPlayerBody` (default) and a full-screen-ish `ExpandedPlayerBody` (up to 80% of screen height). The transition is a continuous `Animatable<Float>` drag progress (0f–1f), not a boolean toggle — the card's height is `lerp`'d between a fixed collapsed height and 80% of the available height on every frame of the drag, so it visibly grows/shrinks under the finger instead of snapping at a fixed point (content still switches between the two bodies at `dragProgress > 0.5f`). Gesture logic lives in `QueueScreen.kt`, not a separate library — no `BottomSheetScaffold`/`ModalBottomSheet` is used.

`DragHandle` deliberately lives as a sibling *below* the `Card`, not nested inside either content body: nesting it inside meant the handle — and its in-flight gesture — got disposed and remounted the moment a drag crossed the halfway content-swap point, aborting the gesture; separately, `Card` clips its children to its own rounded-rect bounds, which was cutting off half of the handle's enlarged touch target back when the handle sat at the card's bottom edge. The touch target itself is grown well past the visible 4dp pill via a custom `expandTouchTarget` layout modifier (measures the touch-handling node larger than the size it reports upward, so the enlarged region doesn't affect surrounding layout/spacing) — note that `Modifier.clip()` also restricts hit-testing to its own bounds, so the pill's `clip`/`background` have to live on an inner, unclipped decorative child rather than the same node `pointerInput`/`draggable` is attached to, or the clip silently cancels the expanded region back out.

Releasing the drag also checks fling velocity (`Modifier.draggable`'s `onDragStopped`, converted to progress-units/second — `1.0` means "would cross the whole collapsed-to-expanded range in a second" — so the threshold, `FLING_VELOCITY_THRESHOLD`, is independent of screen density/size) before falling back to "which side is drag progress closer to." A fast short flick commits to fully opening/closing even if the drag never crossed the halfway mark.

The expanded layout adds skip ±30s/2min, a speed-cycling button, and mark-as-played, alongside the always-visible progress slider both layouts share via `PlaybackProgressSlider`. That slider overrides Material3's default track (`@OptIn(ExperimentalMaterial3Api::class)`, since customizing a `Slider`'s `track` slot means passing per-`SliderState` composables) with `LogoTiledTrack`: a thick (28dp) bar whose filled portion is painted with the app logo (`R.drawable.schmodcast_logo`) tiled edge-to-edge over a `SchmodcastNavy` fill via `ShaderBrush(ImageShader(...))`, rather than a solid color. The bitmap is pre-scaled (via `BitmapFactory.Options.inSampleSize`, not a full-res decode) to roughly the track's pixel height before being handed to `ImageShader` — otherwise it tiles at the source PNG's native resolution instead of a fixed on-screen size. The source PNG is an opaque RGB square (navy rounded-badge logo on a near-white margin, no alpha channel) — `keyOutNearWhite` chroma-keys that near-white margin to transparent before tiling, so repeats blend into the navy fill drawn underneath instead of each one carrying its own visible white square. The track's unfilled background deliberately uses `colorScheme.outlineVariant`, not `surfaceVariant`: under this app's dynamic (Material You) theming, `surfaceVariant` lands close enough to `NowPlayingCard`'s own container color to read as invisible against it — `outlineVariant` is the same color the drag handle pill already relies on for contrast in this card.

`ExpandedPlayerBody`'s artwork, spacers, and transport/play-pause button sizes scale down via a `chromeScale` factor (a `BoxWithConstraints` reading the Card's actual available height) rather than staying fixed dp values — confirmed as a real bug on a physical device (Pixel, 420dpi, 1.15x system font scale), where the fixed 80%-of-screen card height was tall enough at 1x font scale but not once the two-line title/podcast-name text grew, silently clipping the entire download/speed/mark-played row with only a sliver of the speed pill's rounded top edge visible under the Card's clip. `chromeScale` combines how much shorter than a 620dp reference the available height is with how much `LocalDensity.current.fontScale` has grown the text beyond 1x, and shrinks only the non-text chrome (never the `Text` composables themselves — that would fight the user's own accessibility setting), clamped to a `0.7f` floor. The pre-existing `verticalScroll` on this Column stays as a fallback for whatever this heuristic doesn't fully cover (e.g. font scales well beyond what was tested).

Tapping an episode row in the "Up Next" list (`UpNextRow`) loads that episode into the player out of turn, without disturbing the queue's date order — see Playback below for how this is threaded through to the service. The now-playing card always reflects whichever episode is actually loaded in the player (`queue.firstOrNull { it.id == playbackState.currentEpisodeId } ?: queue.first()`), not just the queue head. "Up Next" deliberately still lists the full queue, including whatever's currently loaded — removing it from the list read as the episode vanishing — so `UpNextRow` instead takes an `isSelected` flag (`episode.id == nowPlaying.id`) and highlights that row (teal tint, bold title, play glyph) in place rather than promoting/hiding it.

### Playback
`playback/PlaybackService.kt` is a Media3 `MediaLibraryService` (a `MediaSessionService` subtype that also serves a browsable content tree — see Android Auto below) + `ExoPlayer`, giving background playback with lock-screen/notification controls (requires `FOREGROUND_SERVICE_MEDIA_PLAYBACK` + `POST_NOTIFICATIONS` permissions declared in the manifest; `POST_NOTIFICATIONS` is requested at runtime from `MainActivity` on API 33+; the service is `android:exported="true"` specifically so system components other than this app's own `MainActivity` — Android Auto chief among them — can bind to it at all). It is the sole source of truth for "what's playing":
- It collects `EpisodeRepository.queue` directly (not through a ViewModel) and keeps it as `latestQueue`.
- ExoPlayer's own timeline holds the *entire* queue at once, not just the current episode: `loadEpisode(episode, autoPlay)` calls `player.setMediaItems(...)` with `episode` at index 0 and the rest of `latestQueue` (its existing date order, minus `episode`) following it, seeking to `episode.lastPositionMs` via `setMediaItems`'s own `startPositionMs` param. This is what lets Android Auto's built-in Queue screen show real upcoming episodes instead of just the one playing now (see Android Auto below) — the same mechanism a real ExoPlayer playlist app like YouTube Music relies on for that screen.
- Natural completion now splits across two paths, depending on whether the timeline already has a next item queued up:
  - Finishing any item except the last fires `Player.Listener.onMediaItemTransition` with reason `MEDIA_ITEM_TRANSITION_REASON_AUTO` — ExoPlayer has already auto-advanced on its own. That advance is treated as a suggestion, not authority: the handler re-derives the true next episode from `latestQueue` (excluding whichever one just finished) and, if it disagrees with whatever ExoPlayer picked (the timeline's tail is only as fresh as the last `refreshTail()` call), forcibly calls `loadEpisode` to correct onto the right episode instead of leaving ExoPlayer's already-started guess in place. When they agree, it just adopts the new item as current, seeks it to its own `lastPositionMs` if it was already partway through (unlike `loadEpisode`, the tail items built by `orderedMediaItems`/`refreshTail` carry no position info of their own), and trims the now-finished leading item(s) off the timeline (`player.removeMediaItems(0, player.currentMediaItemIndex)`) so index 0 is "current" again — an invariant `refreshTail()` (and anything else that (re)builds a timeline expecting to start at index 0) depends on.
  - Finishing the very last item in the timeline instead reaches `Player.STATE_ENDED` (there's nothing queued to auto-advance to), which calls `episodeRepository.markPlayed(...)` and leaves the queue-collector below to pick up the new head once the queue `Flow` re-emits without it.
- The queue-collector branches on every `episodeRepository.queue` emission: if `currentEpisodeId` is still present in the new list, it calls `refreshTail()` (replaces everything after the currently-playing index with a freshly-ordered tail, never touching the playing item itself, so a background refresh — or the 5s position-save ticker, which also re-triggers this Flow — never interrupts playback); if `currentEpisodeId` disappeared without `onMediaItemTransition` already having handled it (e.g. the phone UI's manual "mark as played" bypasses the player entirely), it advances to the new head itself.
- `ui/queue/QueueViewModel.kt` never touches the `ExoPlayer` directly — it connects a Media3 `MediaController` to `PlaybackService` via `SessionToken` and issues transport commands (play/pause, seek, ±2min/30s skip, playback speed via `setPlaybackSpeed`), polling playback position and speed on a 500ms ticker while playing. A manual "mark as played" tap instead calls `episodeRepository.markPlayed(...)` directly from the ViewModel, bypassing the controller entirely — the queue-collector branch above handles that case the same way it would a `PlaybackService`-unaware disappearance.
- Tapping an episode in the queue UI (`QueueViewModel.onEpisodeClick`) sends a Media3 custom session command (`PlaybackService.CUSTOM_COMMAND_PLAY_EPISODE`, episode ID as a `Bundle` extra) rather than going through a regular transport command, because loading an arbitrary episode — as opposed to play/pause/seek on whatever's already loaded — needs to run inside the service so it can rebuild the timeline around it and update `PlaybackService`'s own bookkeeping. `PlaybackService.sessionCallback` (a `MediaLibrarySession.Callback`) declares and handles this command, looks the episode up in `latestQueue`, and calls `loadEpisode(episode, autoPlay = false)` — matching the load-without-autoplay behavior already used for the initial queue head, so the user still has to press play. `loadEpisode` builds the tapped episode's own ordered timeline (itself at index 0, the *true* queue head next — not whatever happened to be date-adjacent to it), so once it naturally finishes, the transition handling above resumes playing whatever is at the head with no special-casing — playing an out-of-order episode doesn't touch queue order or need its own "what's next" logic.

Hardware transport buttons (a car's steering wheel, a Bluetooth headset, a wired remote, the phone's own lock-screen/notification controls) send standard media-key events, which Media3 translates into `Player.COMMAND_SEEK_TO_NEXT`/`_PREVIOUS` (skip-to-adjacent-*episode*, since the timeline holds the whole queue) rather than reaching any of `PlaybackService`'s custom session commands — those only exist for touch UI (the phone app, Android Auto's Now Playing screen), hardware buttons have no way to invoke them. Left alone, a physical next/previous press would jump to a different episode entirely, which isn't a good idea to risk while driving — so `sessionCallback.onPlayerCommandRequest` intercepts `COMMAND_SEEK_TO_NEXT`/`_PREVIOUS` (and their `_MEDIA_ITEM` variants) and redirects them to the same `skipForward()`/`skipBack()` (±2min/30s) the custom actions use, returning `SessionResult.RESULT_INFO_SKIPPED` so ExoPlayer's own default next/previous-episode handling never runs. This is a blanket policy across every hardware/remote surface, not just Android Auto, by design — confirmed on-device via `adb shell cmd media_session dispatch next`/`previous` (the actual media-button dispatch path; `adb shell input keyevent` does *not* reach a session correctly, since it injects into the focused window rather than going through `MediaSessionManager`'s dispatch), which showed exact ±120000ms/-30000ms position deltas with the active episode unchanged. `onPlayerCommandRequest` is deprecated in media3-session 1.10.1 with no non-deprecated replacement that still supports intercepting-and-substituting a command, so it's suppressed deliberately at the call site.

Any change to episode fetching, queue filtering, or playback ordering should account for this split: `EpisodeRepository`/Room is the single source of truth for queue contents, and `PlaybackService` reacts to it rather than being told what to play by the UI layer.

### Android Auto
The service is a `MediaLibraryService` rather than a plain `MediaSessionService` specifically so Android Auto (and any other `MediaBrowser` client) can discover and browse it. Discovery needs two things beyond the Media3 wiring itself: a `<meta-data>` in the manifest pointing at `res/xml/automotive_app_desc.xml` (`<uses name="media"/>`), and the service's intent-filter carrying *both* the Media3 action (`androidx.media3.session.MediaLibraryService`) and the legacy `android.media.browse.MediaBrowserService` action — Auto's own app-discovery scan looks for the legacy action specifically, confirmed by querying `PackageManager` directly; the Media3 action alone left the app invisible to Auto. The service also has to be `android:exported="true"` (see Playback above) — without it, Auto's process gets a `SecurityException` binding to it, silently failing with no indication in the app itself.

`sessionCallback`'s `onGetLibraryRoot`/`onGetChildren`/`onGetItem` expose a browse tree, but it's deliberately two levels (invisible root → one browsable "Queue" folder → the episodes), not a flat root-to-episodes list: Android Auto treats a root's direct children as browsable tabs, and a root whose children are playable leaves directly gets collapsed/skipped straight to the Now Playing screen instead of ever showing a browse screen — confirmed against Android Auto's own documented structure and Media3's issue tracker after a flat root initially failed to show anything. `onSetMediaItems` resolves a tapped browsed episode back to a real `Episode` (the incoming `MediaItem` only carries a `mediaId`, no `Uri` — that's `browsableMediaItem`, distinct from `loadEpisode`'s `playableMediaItem`) and returns the same full ordered timeline `loadEpisode` would build, so tapping an episode from Auto's browse tree behaves identically to tapping it in the phone UI.

In practice, testing via the Desktop Head Unit found this Auto version always opens straight to Now Playing rather than the browse tree whenever a session is already active — which, given this app auto-loads an episode on startup, is essentially always — regardless of tap entry point (app grid icon, current-media shortcut, or DHU's simulated search key). What actually surfaces the queue in Auto's UI is its built-in Queue screen, driven by the real multi-item ExoPlayer timeline described under Playback above, not this browse tree. The browse tree is still left in place (it's correct per Google's documented structure, and other clients — voice, search, other head units — may still reach it), but don't assume it's how users will actually see the queue in Auto.

Auto's Now Playing screen only renders a handful of custom action slots, each needing an icon rather than a Compose button, so the expanded player's skip ±30s/+2min and speed-cycle actions (`QueueScreen`'s `TransportButton`/`SpeedCycleButton`) are mirrored as `SessionCommand`s (`CUSTOM_COMMAND_SKIP_BACK`/`_SKIP_FORWARD`/`_CYCLE_SPEED`) rather than relying on Media3's generic seek-back/seek-forward player commands — those apply one symmetric increment to both directions, which doesn't fit this app's asymmetric 30s-back/2min-forward skip. `sessionCallback` advertises them via `MediaSession.ConnectionResult.AcceptedResultBuilder.setCustomLayout(...)` in `onConnect`, using `CommandButton.Builder(...)` with this app's own hand-drawn `ic_skip_back`/`ic_skip_forward`/`ic_speed` vectors set via `.setCustomIconResId(...)`. Skip back/forward use the generic (unnumbered) predefined `CommandButton.ICON_SKIP_BACK`/`ICON_SKIP_FORWARD` constants rather than `ICON_UNDEFINED`, so Auto has a real signal that these are skip actions and not previous/next-*episode* ones (see the chevron note below); speed stays `ICON_UNDEFINED` (no generic "cycle speed" predefined constant exists) with `.setSlots(SLOT_FORWARD_SECONDARY, SLOT_OVERFLOW)` — a slot preference *order*, not a set, so a host template that allots zero buttons to `SLOT_FORWARD_SECONDARY` (Auto's full-screen Now Playing template does, by default, per `CommandButton.DisplayConstraints`) falls back to `SLOT_OVERFLOW` (unlimited by default) instead of dropping the button entirely.

**The custom layout has to be re-pushed session-wide on every connect, not just set once in `onConnect` — this was a real bug, not a platform limitation.** `ConnectionResult.setCustomLayout(...)` in `onConnect` only seeds *that one connecting controller's* initial layout; it doesn't update the session-wide legacy `PlaybackStateCompat` that Auto's persistent rendering and `dumpsys media_session` actually read (confirmed by decompiling `media3-session-1.10.1`'s `MediaSessionLegacyStub`/`CommandButton` sources directly, not just by observing symptoms). Without an explicit push, the custom action list only appeared briefly — whatever seeded the legacy stub at the service's own construction — and silently reverted to empty (`custom actions=[]` in `dumpsys`) once Auto's real controller connected, which is exactly backwards from what a screenshot taken moments earlier suggested and caused this to be misreported as fixed once already. Fixed by adding `sessionCallback.onPostConnect` (the hook `MediaSession.Callback.onConnect`'s own docs point to for exactly this) to call `session.setCustomLayout(customLayout())` on every connect, verified by checking `dumpsys` after a real settle period (20s+, past when Auto's controller has fully connected) rather than immediately after install. This also means the earlier documented conclusion that "every slot other than `SLOT_BACK`/`SLOT_FORWARD` always shows the same generic glyph, never the app's own resource" was likely partly a symptom of this same bug (the custom action was never really reaching Auto with a populated icon at all) rather than purely a platform-enforced substitution — after the fix, `dumpsys` shows the real `ic_skip_back`/`ic_skip_forward`/`ic_speed` drawable resource IDs flowing through, and Auto's full-screen Now Playing rendered three visibly distinct icons where before it showed one generic glyph or nothing.

**`SLOT_BACK`/`SLOT_FORWARD` rendering as the standard previous/next chevrons, however, is a separate, confirmed-unfixable constraint — not an icon problem at all.** Tracing `MediaSessionLegacyStub.createPlaybackStateCompat` shows the chevrons come from the legacy `ACTION_SKIP_TO_PREVIOUS`/`_NEXT` bits, set purely from whether `Player.COMMAND_SEEK_TO_PREVIOUS`/`_NEXT` are in the session's negotiated available player commands — entirely independent of whatever `CommandButton` this app puts in those slots or what icon it carries. That's the same availability flag `ConnectedControllersManager.isPlayerCommandAvailable` checks before a hardware media-button press (steering wheel/Bluetooth/wired remote) is ever allowed to reach `onPlayerCommandRequest` (see the hardware-button paragraph below) — so removing those commands to kill the chevrons would also silently break hardware-button dispatch entirely (the request would be dropped in `MediaSessionLegacyStub.dispatchSessionTaskWithPlayerCommand` before ever reaching our redirect). Confirmed via source tracing, not just observation; raised with the app owner rather than resolved unilaterally, and the decision was to keep the chevrons rather than lose hardware-button skip.

A real third-party app (Pocket Casts) shows a live custom speed icon in this same DHU with its `dumpsys` custom-action extras coming back `null`, consistent with it bypassing Media3's `CommandButton`/slot system entirely via the older `MediaSessionCompat` API.

The skip/speed amounts and the speed-cycle sequence live in `playback/PlaybackTuning.kt` (`SKIP_BACK_MS`/`SKIP_FORWARD_MS`/`SPEED_OPTIONS`/`nextSpeed`/`formatSpeedLabel`), shared between `PlaybackService`'s custom-command handlers (which act on `player` directly) and `QueueViewModel`/`QueueScreen` (which act through a `MediaController`), so the phone UI and Auto can't drift to different skip amounts or speed steps — `SPEED_OPTIONS` is `1/1.2/1.4/1.6/1.8/2x`, unchanged from before this work. Mark-as-played was left phone-only per the original plan, since it already bypasses the session entirely via `episodeRepository.markPlayed(...)` and natural-completion auto-advance covers the in-car case.

### Home-screen widget
`widget/NowPlayingWidgetProvider.kt` is a classic `AppWidgetProvider` + `RemoteViews` widget (no Jetpack Glance — kept dependency-free, consistent with this app's existing preference for hand-rolled solutions over extra libraries), showing the current episode's artwork, play/pause, and the two skip buttons full-width on the home screen. It follows the same rule as the persistent notification: `PlaybackService` is the sole owner of "what's playing" and pushes `RemoteViews` to the widget itself (`NowPlayingWidgetProvider.pushUpdate`) from every place it already updates `currentEpisodeId`/play state (`loadEpisode`, `onIsPlayingChanged`, the `onMediaItemTransition` branch that settles onto a new episode without going through `loadEpisode`) — there's no separate `MediaController`, broadcast, or direct Room read acting as a second source of truth. `NowPlayingWidgetProvider.onUpdate` (system-triggered: widget added/resized, device reboot) only renders a placeholder, since a `BroadcastReceiver` callback must return quickly and isn't a good fit for starting/binding the service itself — real state arrives moments later once `PlaybackService` is (or becomes) alive.

The widget's transport buttons can't hold a `MediaController` connection the way the phone UI/Auto do, so instead of `SessionCommand`s they're plain `Intent` actions (`PlaybackService.ACTION_PLAY_PAUSE`/`_SKIP_BACK`/`_SKIP_FORWARD`) sent via `PendingIntent.getService(...)` and handled in an `onStartCommand` override — anything that isn't one of these three actions still falls through to `super.onStartCommand(...)` so Media3's own media-button handling keeps working. Tapping play on a cold start (process killed, nothing prepared yet) can't call `player.play()` immediately, so it sets `pendingAutoPlayOnLoad = true` instead; the initial-load branch in `onCreate`'s queue collector reads that flag when it calls `loadEpisode` for the first time, and `loadEpisode` itself resets it once consumed.

Artwork is fetched with a plain synchronous OkHttp request (reusing `data.remote.NetworkModule.okHttpClient`, the same client already wired up for the iTunes API) and decoded via `BitmapFactory` with `inSampleSize` downsampling to roughly the widget's artwork `ImageView` size — deliberately not through Coil3, since Coil3 wraps decoded images in its own `coil3.Image` type rather than a raw `Bitmap`, which `RemoteViews.setImageViewBitmap` needs; reusing the plain OkHttp client already in the codebase avoids adding that conversion surface for a single call site. Artwork is per-podcast rather than per-episode, so it's cached by URL (one entry) rather than by episode id, avoiding a re-fetch when the queue moves between episodes of the same podcast.

### Background refresh & proactive downloads
`data/work/QueueRefreshWorker.kt` and `data/work/EpisodeDownloadWorker.kt` are `CoroutineWorker`s (WorkManager) that keep the queue and downloads current even when the app isn't open — everything under Data layer above only runs while some component (`QueueViewModel`, `PlaybackService`) is alive to trigger it. Like everywhere else in the app, a `Worker` reaches the manual-DI singletons via `applicationContext.episodeRepository()`/`.subscriptionsRepository()`/`.episodeDownloadManager()` rather than a `WorkerFactory`.

- `QueueRefreshWorker` is a periodic job (hourly, `NetworkType.CONNECTED` — any connection, since an RSS fetch is cheap) scheduled once from `SchmodcastApplication.onCreate` via `enqueueUniquePeriodicWork(..., ExistingPeriodicWorkPolicy.KEEP, ...)` (`KEEP` so relaunching the app doesn't reset its schedule). It does exactly what `QueueViewModel.init` does on the UI side — snapshot subscriptions, `EpisodeRepository.refreshAll`, `pruneOldEpisodes` — then enqueues `EpisodeDownloadWorker`.
- `EpisodeDownloadWorker` is a one-off job constrained to `NetworkType.UNMETERED`, so WorkManager itself withholds it until on WiFi. It reads `EpisodeRepository.nextUndownloaded(3)` (backed by `EpisodeDao.getUndownloaded`, the same unplayed/newest-first ordering as `observeQueue()` but filtered to `localFilePath IS NULL`) and calls the existing `EpisodeDownloadManager.download(episode)` for each — no changes needed to the download logic itself, since it already persists `localFilePath` to Room regardless of who triggered it. Because `download()` launches on `EpisodeDownloadManager`'s own app-scoped `CoroutineScope` rather than the Worker's, `doWork()` awaits completion by suspending on `EpisodeDownloadManager.states.first { ... Downloaded || ... Failed }` instead of the launched job directly — which also means cancelling/replacing the Worker (re-enqueued hourly via `ExistingWorkPolicy.REPLACE`) doesn't abort an in-flight download, only the Worker's own wait.

### Theming
`ui/theme/Theme.kt`'s `SchmodcastTheme` defaults `dynamicColor = true`, so on API 31+ devices the app actually renders Material You's wallpaper-derived palette, not the static `SchmodcastNavy`/`SchmodcastOrange`/`SchmodcastCream`/`SchmodcastTeal` scheme sitting next to it in `Color.kt` — `MaterialTheme.colorScheme.*` will not reflect the brand colors on those devices. Composables that need the actual logo colors regardless of theme (e.g. the expanded player's play/pause button and skip buttons) reference the `Schmodcast*` constants from `Color.kt` directly instead of going through `MaterialTheme.colorScheme`.
